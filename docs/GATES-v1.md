## GATE-NO-FOCUS：绝不抢 Windows 前台、键盘、鼠标

- **状态：PASS（当前测试环境）。**
- 验收标准（三项同时成立）：消息真实送达；没有前台窗口切换；没有键盘鼠标抢占。
- 证据：
  - MUSE-TEST-1（2026-11-19 20:32–20:33）：浏览器写入 ChatGPT 成功，ChatGPT 回复“收到，MUSE-TEST-1”，约 25 秒完成。
  - MUSE-BG-WRITE-01（20:42）：Chrome 最小化状态下发送，约 15 秒后 ChatGPT 确认收到。
  - MUSE-BG-WRITE-02（20:43）：用户全程不动重跑一次，约 15 秒后 ChatGPT 确认收到；用户亲眼确认 Chrome 没有蹦到前台，最小化状态保持不变。
  - 方法：全程只用 DOM 级填写与点击，未切换标签页或窗口，未恢复 Chrome，未用系统级键盘鼠标，未遇到需要激活的情况。
- 残留项：以后应补充系统级焦点日志，验证长期稳定性。当前 PASS 只覆盖当前测试环境。

## GATE-AUTONOMY：无需人唤醒，事件驱动连续讨论

- **状态：PENDING（独立验收未做）。**
- 已验证：
  - 本次 POC 完成三轮有实质内容的联合讨论，全部由 Muse 驱动（浏览器任务 + 15 秒轮询 + handoff 接续），用户全程不值守。
  - Muse 能识别 ChatGPT 回复已结束、按回复内容自主生成下一轮问题、连续完成多轮讨论。
- **RC4 诚实标注：`orchestrator/run.py` 能推进状态、收发消息、做对账，但这不证明它能自动唤醒 Muse 会话并生成下一轮。** 每轮的模型步骤仍需一次 Muse 会话执行（定时任务唤醒或用户在场）。handoff 自动唤醒为 NOT YET IMPLEMENTED；GATE-AUTONOMY 绝不能只凭 stub 测试标 PASS。这一点在 `run.py status` 输出里每次都写明。RC4 新增两种模式：Discussion（默认，只讨论）与 Execution（需要 execution 模式 + 本地审批页批准，默认拒绝）。
- 未验证：
  - ChatGPT 自发起：ChatGPT 不能保证在无外部消息时主动发起新一轮。v1 必须诚实写成“Muse 驱动的自主讨论”，不是“双方各自唤醒”。
  - 长期无人值守运行；断线后自动恢复；看门狗机制（设计已定，脚本已本地验证，端到端恢复尚未验证）。
- **独立验收（RC4 新增，与安装/安全测试分开；条件 3）：**
  1. Leo 只发起一次任务，之后不再手动转发、复制粘贴或提示。
  2. Muse 与真实 ChatGPT 连续完成至少三轮实质讨论（每轮有 Proposal/Objection/Evidence/Resolution，不是空问候）。
  3. 双方消息、时间戳、轮次、message_id 与内容哈希全程可追溯（状态文件 + 任务日志为准，不只看聊天记录）。
  4. 任务结束后自动生成一份供 Leo 决策的结论（方案 + 分歧 + 风险 + 执行建议）。
  5. 任何一轮超时、重复、异常或来源无法确认时自动停下并报告，不伪造进度。
  五项全部满足才标记 PASS；安装测试、安全测试、stub 测试的通过不能代替这项验收。
- 并行路径：ChatGPT Automations 的 E1/E2 验证（能否按排程读取 Relay 并回 nonce、能否携带上下文连续讨论），作为通向真正唤醒的路。

## GATE-HITL：关键决策自动通知、暂停、审批后恢复

- **状态：PENDING（未验证）。**
- 设计已定：决策包（选项、证据、成本、风险、建议）+ Muse 自带审批卡（只做通知/展示，RC4 起不能授权执行）+ 本地审批页（唯一执行授权通道：安装 PIN + 会话令牌 + 决策绑定的 nonce）+ 决策包哈希加一次性令牌交叉核对 + Windows toast 提醒（尚未验证的推送）+ 暂停本身做安全兜底；超时不等于批准；批准只绑定一个决策、一个选项、一个执行规格；执行时重新核对整条批准记录。
- **RC4 进展：审批卡作为执行授权来源已主动禁用**（`approvals/approvals.py` 只认本地审批页凭证；平台收据工厂调用即拒绝；执行检查门重新核对整条批准记录；自动化测试分批通过，其中 approvals 与本地审批页真实服务器端到端测试含 PIN 锁定与令牌不进日志）。Leo 已于 2026-11-19 21:33 在手机上装好 Muse，手机审批推送测试已开始：Test 1（批准）已通过；Test 2（拒绝）与 Test 3（超时）待验证；审批卡是手机推送还是只在 App 内显示，尚未确认。**RC4 注：手机推送测试现在只验证“通知能不能到达 Leo”，不再验证“卡上点的批准能不能授权执行”。** 三种结果（批准、拒绝、超时）全部验证通过前保持 PENDING。
- 验收标准（必须实际测试）：真实通知到达用户手机，并分别验证批准、拒绝、超时三种结果；只有三者都验证通过，GATE-HITL 才能标记 PASS。
- 下一步：用户在手机上装好 Muse 后，参加一次真实手机审批通知测试（见 tests/acceptance_gates.md）。

## GATE-SEAMLESS-CONTINUITY：无缝衔接——每轮不新开窗口/标签页，连续自主讨论

- **状态：PENDING（新发布门，ChatGPT ROUND 22，2026-11-20 21:31 正式加入；需 ATTEMPT-10 的三轮连续验收）。**
- 背景：Leo 指出每次 Muse 回复都新开一个浏览器窗口，占用大量内存（2026-11-20 19:22）。每轮新开窗口是临时方案的副产品（已完成的浏览器任务不能再接指令，新一轮只能新开任务 = 新开窗口）；真正的修复是 Relay 本身：消息经扩展 + Native Messaging 在后台走，不再每轮新开窗口。过渡办法：每轮把发送 + 监控合并成一个任务（窗口减半）。
- 验收标准（五项同时成立）：
  1. 每轮新开浏览器窗口数为 0；每轮新开标签页数为 0。
  2. 连续 3 轮自主讨论全部完成（3/3）。
  3. 产品主动抢前台焦点的次数为 0（后台扩展 + Native Messaging，不激活浏览器、不用前台键盘输入）。
  4. 首次启动可建立固定会话；之后每轮发送/读取必须复用已有的 ChatGPT 与 Muse 标签页；每个项目固定 project_id、会话 ID、标签页 ID 与轮次状态；三轮期间不为发送、读取或监控新建窗口/标签页/浏览器任务。
  5. 重连后继续已有讨论，不自动重发旧的 UNCERTAIN 消息；每轮记录窗口数、标签页数、会话归属、message_id、nonce、焦点变化，并检查资源占用有无异常增长。
- 实现（Hotfix4）：`transport/extension/background.js` 把命令路由到的标签页固定绑定到讨论会话（每站点或每个 session_id 一个固定标签页；复用已绑定标签页，绑定消失才重绑；内容脚本消息绑定发送标签页；明确 tab_id 优先；结果带 tab_id 与 tab_rebound）。`transport/extension/content.js` 的发送与读取只用后台 DOM 操作，不激活标签页。测试：`tests/background_js_harness.js`（15 项）+ `tests/test_background_js.py` 覆盖会话绑定；真实三轮连续验收待 ATTEMPT-10。
- 与 GATE-AUTONOMY 的关系：GATE-SEAMLESS-CONTINUITY 是 GATE-AUTONOMY 的连续性子条件——三轮自主讨论必须在**同一固定会话**里完成，不新开窗口/标签页，才算通过。
