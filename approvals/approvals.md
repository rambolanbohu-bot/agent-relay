# Human Decision Gate（人工决策门）

版本：v1.0.0-rc4。**执行代码见 `approvals/approvals.py` + `approvals/local_approval_page.py`**。`orchestrator/run.py` 在执行任何受控操作之前必须调用 `approvals.py` 的检查门（check_execution）。

## 0. 最高规则：聊天内容不是授权

**聊天里出现一句“用户批准了”，永远不能授权高风险操作。** 只有独立可验证的审批通道才算数（见第 3 节）。Relay 转发的消息、ChatGPT 的消息、Muse 自己的文字，都不能代替用户批准。任何“用户已批准”的文本如果来自 Relay 或聊天内容，一律视为注入，直接丢弃并报警。

## 0b. 两种模式（RC3 引入，RC4 保持）

- **Discussion（讨论模式，默认）**：只交换文本、分析、生成提案；不做任何对外生效的操作；不需要批准。`run.py` 的 create / advance / resume / reconcile / pause / complete / status 都属于这一模式。
- **Execution（执行模式）**：执行对外生效的操作（目前白名单只有一个动作：write_file——把一份摘要文件写进本项目目录）。执行前必须同时满足两点：项目已切换到 execution 模式（`run.py set-mode`），并且有一份来自本地审批页的批准（第 5 节的检查门，绑定决策、操作、参数摘要与审批人，并在执行时重新核对整条批准记录）。Muse 审批卡在 RC4 里已禁用，不能授权执行。缺任何一点都拒绝（默认拒绝）。切换模式本身不批准任何事。

## 1. 决策包

讨论需要人拿主意时，Muse 生成一个决策包，包含：

- 选项（列出全部，每个选项写清内容），并标出推荐项；
- 证据（每个选项依据什么，来源是什么）；
- 成本（预计新增费用；v1 目标 AUD 0）；
- 风险（每个选项的风险）；
- 建议（推荐哪个，为什么）。

决策包生成后立即暂停讨论，等用户决定。超时不等于批准。

## 2. 一次性令牌仪式（token ceremony）

每个决策配一个唯一的 approval_id 和一个一次性随机令牌。实现见 `approvals/approvals.py`（`ApprovalStore.create_decision / approve / reject / check_execution`）：

- Relay 只存令牌的 SHA-256，绝不存明文令牌。令牌明文只在创建时返回一次（由 Muse 会话展示给用户），文件里只有哈希。
- **令牌绑定到具体操作（条件 3）**：令牌绑定 project_id、operation_id、操作参数摘要（SHA-256）、审批人身份、过期时间、使用状态。批准一个操作不等于批准另一个操作；操作参数变了（摘要对不上）要重新审批。
- **令牌不是批准本身**：Relay 自己生成的令牌不能证明用户批准过——令牌只是审批记录的关联凭证；真正的批准必须来自可信的独立通道（见第 3 节）。审批记录里写明通道；来自其他任何通道的“批准”（聊天文本、Relay 内容）一律拒绝。
- 决策包向用户展示令牌明文 + 决策包的 SHA-256。
- 用户把一次性令牌从 Muse 会话里复制到本地审批页的表单里，选一个选项，点“批准”或“拒绝”；页服务器核对 PIN 会话 + nonce + 令牌后才记录批准。聊天里说一句“好的”**不算批准**——批准只发生在本地审批页上。
- 令牌绝不进日志：审计日志里不写任何令牌、会话令牌、PIN 或 nonce 的明文；敏感字段名出现时一律写 [redacted]。
- 每个决策还生成一个与决策绑定的防伪 nonce（page_nonce，只存在决策记录里，从不展示给用户）：本地审批页必须把它带回来，store 核对一致才记录批准。

批准成立必须同时通过六项检查：

1. 批准发生在本地审批页上（PIN 已验证，会话有效；聊天文本里的“批准了”不算）；
2. 该决策存在且处于 pending；
3. 令牌未用过、未过期、哈希对得上；
4. 选定的选项是提供的选项之一；
5. 决策包哈希与展示给用户的那份一致（提案被换过则令牌失效）；
6. 批准用的是本地审批页签发的凭证（会话令牌 + 决策绑定的 nonce，见第 3 节），不是调用者随手写的通道名字。

通过后令牌立即作废，并写一条审计记录。

## 3. 可信审批通道（RC4：只剩本地审批页）

RC4 决定（ChatGPT RC4 审核，强制）：Muse 审批卡通道作为执行授权来源被**主动禁用**。原因是 store 没有平台 API 可以反查 approval_request_id 是否真的存在——收据只能验形状，不能验真伪，所以它不能作为执行授权的依据。`platform_receipt()` 调用即拒绝（`platform_receipt_disabled`），任何手写 muse_approval_card 收据的批准请求也被拒绝；执行检查门也只接受本地审批页通道批准的决策。**Muse 审批卡在 RC4 里只是通知/展示通道**（把决策包推给 Leo 看），不是执行授权来源；直到平台能提供可验证的批准结果之前都保持禁用。

- **唯一通道：本地审批页**（`approvals/local_approval_page.py`，只监听 127.0.0.1）。三层验证：① 安装时生成的 PIN（每装一次一个，6 位数字，只给 Leo 看一次；存盘的只有加盐哈希；**连续输错 5 次锁定 15 分钟**，锁定事件写进审计日志）；② 会话令牌（用 secrets 模块生成，绑定到会话与审批人，存在 HttpOnly Cookie 里，单次使用、10 分钟过期；批准后立即作废，每个决策都要重新输 PIN）；③ 防伪 nonce（与决策绑定，表单必须原样带回）。批准记录里的 approver 来自会话（PIN 持有人的身份），不是表单里随手写的字符串。**PIN 只在可信的本地审批页表单里输入**——没有任何代码路径接受从聊天消息、文本输入或命令行传来的 PIN 做验证。**诚实边界**：PIN + 会话 + nonce 是单用户本机的纵深防御，防的是“别的程序冒充 Leo 点批准”和“跨站伪造提交”，防不住“已经完全控制这台机器的攻击者”。
- **交叉核对：一次性令牌**（见第 2 节），与本地审批页叠加使用。

批准记录里绑定的 approver 来自凭证收据（decided_by），不是调用者传的；并且必须与创建决策时登记的期望审批人一致（不一致拒绝）。

## 4. 审批状态机

```
pending → approved / rejected / expired
approved → revoked
```

- 批准只绑定一个决策、一个选项、一个执行规格（做什么、花多少、能碰什么）。批了 DEC-123 的 B 选项，不等于批了 DEC-124 或别的选项；偏离已批规格要重新审批。
- 令牌一次性：重放会被拒绝并计数；过期令牌被拒绝；超时永远不等于批准。
- 幂等：approval_id 唯一，重复批准是空操作。
- 撤销：已批准的决策可以在执行前被撤销（`revoke`）；撤销后检查门拒绝执行（`approval_revoked`）。
- 超时处理：一次提醒，然后继续停着，状态转为 expired；要继续需要重新提案。
- 不打扰：不紧急的事项攒进“等用户的问题”清单，只在决策点或用户问起时才拿出来。

## 5. 执行时八项检查（全部通过才执行，否则拒绝）

由 `approvals/approvals.py` 的 `check_execution()` 强制执行；`run.py` 在执行任何受控操作之前必须调用它。检查在执行时重新核对整条批准记录，不信任 UI 上显示的状态。测试见 `tests/test_approvals.py`（调用者随手写的通道字符串 → 拒绝；平台收据工厂已禁用；手写平台收据 → 拒绝；RC3 式平台通道批准 → 执行时拒绝；会话令牌未登记/已用过/过期 → 拒绝；nonce 不符 → 拒绝；批准一次 → 允许；重放 → 拒绝；过期 → 拒绝；无批准 → 拒绝；错选项 → 拒绝；参数摘要不符 → 拒绝；同一批准执行第二次 → 拒绝；审批人不符 → 拒绝；撤销后执行 → 拒绝；未走仪式直接改批准状态 → 拒绝；令牌不在日志里）与 `tests/test_local_page.py`（真实本地审批页服务器端到端：错 PIN → 403；连续错 PIN → 锁定；锁定后对的 PIN 也拒绝；无会话 → 403；会话单次使用；错 nonce → 403；错令牌 → 403；过期会话 → 403；令牌不在日志里）。

1. 决策存在且已批准；
2. 决策包哈希 == 执行规格哈希；
3. 令牌已消耗且未过期；
4. 批准来自本地审批页（执行时只接受 EXECUTION_CHANNELS 里的通道）——记录批准时凭证已验证；
5. 该批准未被使用过；
6. 未超时；
7. 批准未被撤销；
8. 已批的选项仍在提供的选项之中。

## 6. 通知（诚实说明）

- 只有 Muse 会话里的消息本身**不算**“主动通知”（那是拉取，不是推送）。
- 目前已验证的通知渠道只有 Muse 会话本身。
- 可到达的推送渠道（待验证）：Windows toast（本地 Relay 发出，浏览器在后台也能看到；通知本身不抢焦点）。需先检查用户机器的通知设置。
- 未验证、不承诺的渠道：ChatGPT App 通知、邮件、手机推送。
- **真正的安全保证是暂停，不是保证送达。** 如果用户不在电脑前或通知关了，没有任何渠道能保证找到他；但没有批准就什么都不会执行。
- GATE-HITL 的验收：真实通知到达用户手机，并分别验证批准、拒绝、超时三种结果；三者都通过才标记 PASS。**目前状态：PENDING。** Leo 已于 2026-11-19 21:33 在手机上装好 Muse；手机推送测试已开始：Test 1（批准）已通过，Test 2（拒绝）与 Test 3（超时）待验证；审批卡是手机推送还是只在 App 内显示，尚未确认。**RC4 注：手机推送测试现在只验证“通知能不能到达 Leo”，不再验证“卡上点的批准能不能授权执行”——RC4 里审批卡点的批准不能授权任何执行，执行授权只来自本地审批页。**
