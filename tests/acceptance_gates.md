# 四道验收门：验收脚本（acceptance_gates.md）

版本：v1.0.0-rc4-hotfix7。每道门按步骤执行，证据以运行日志为准；未通过的步骤不得标为通过。

## GATE-NO-FOCUS：绝不抢 Windows 前台、键盘、鼠标

状态：**PASS（当前测试环境）**——证据见 tests/TEST-RECORDS-v2.md 第 4 节。

复验步骤（任一用户在自己的电脑上重跑）：

1. 打开 Chrome，登录 ChatGPT；把 Chrome 最小化，前台停在别的窗口，全程不动。
2. 让 Muse 发一条带唯一标记的测试消息（例如 `MUSE-BG-WRITE-01`），只用浏览器自身的页面操作。
3. 检查三项：消息是否真实送达（ChatGPT 是否确认收到该标记）；Chrome 是否蹦到前台（用户亲眼确认）；是否用了系统级键盘鼠标（方法记录为准，只用 DOM 操作才算过）。
4. 换一个新标记重跑一次（例如 `MUSE-BG-WRITE-02`），两次都过才算通过。
5. 如果发送必须激活标签页或把 Chrome 带到前台 → 立即停止，该条路标记为不满足零抢焦点。

残留项：长期稳定性需补充系统级焦点日志（当前 PASS 只覆盖当前测试环境）。

## GATE-AUTONOMY：无需人唤醒，连续讨论

状态：**PENDING（独立验收未做）**。三轮实质讨论已完成（Muse 驱动，Leo 全程不值守）；ChatGPT 自发起、长期无人值守、断线自动恢复尚未验证。**安装/安全测试不能代替本验收。**

独立验收步骤（RC4，条件 3）：

1. 用户说“开始讨论：……”后不再发任何消息、不点任何东西、不手动转发、不复制粘贴、不提示。
2. Muse 与真实 ChatGPT 连续完成至少三轮实质讨论，每轮有 Proposal/Objection/Evidence/Resolution，有记录（消息 ID、时间、内容哈希、成功状态）。
3. 检查：Muse 能否识别 ChatGPT 回复已结束；能否在无人干预下生成下一轮问题；三轮是否有实质内容（不是简单回显测试字符串）。
4. 任务结束后自动生成一份供 Leo 决策的结论（方案 + 分歧 + 风险 + 执行建议）。
5. 异常注入：超时、重复消息、异常出现时是否自动停止，不无限循环。
6. 证据要求：须以完整后台任务日志证明轮次由无人值守机制自主触发；光有聊天记录不够。
7. 并行验证（ChatGPT 侧真正唤醒）：E1——ChatGPT Automations 按排程读取 Relay 消息并回 nonce（最多 2 次尝试）；E2——第二次运行携带上下文连续讨论（最多 2 次尝试）。任一通过才启动对应建设；都失败则 v1 保持“Muse 驱动”的诚实标注。

## GATE-HITL：关键决策自动通知、暂停、审批后恢复

状态：**PENDING（未验证）**。设计已定（见 approvals/approvals.md），审批强制检查已实现（见 approvals/approvals.py；RC4 只认本地审批页凭证，平台收据通道已禁用；自动化测试分批通过）。Leo 已于 2026-11-19 21:33 在手机上装好 Muse，手机推送测试已开始：Test 1（批准路径的通知到达）已通过；Test 2（拒绝）与 Test 3（超时）待验证。**RC4 注：手机推送测试现在只验证“通知能不能到达 Leo”，不再验证“卡上点的批准能不能授权执行”——审批卡点的批准不能授权任何执行，执行授权只来自本地审批页。**

验收步骤（需用户本人参加，Leo 手机装好 Muse 后进行）：

1. 准备：用户在手机上装好 Muse 并登录同一账号；确认手机通知权限已开。
2. 触发：Muse 生成一个决策包（选项、证据、成本、风险、建议），进入 AWAITING_APPROVAL，暂停讨论。
3. 通知到达检查：用户确认手机是否收到审批通知（几点几分收到、什么形式：推送还是只在 App 内显示）。
4. 批准路径：用户从通知打开本地审批页，输 PIN、粘贴一次性令牌、选一个选项、点批准 → 检查执行是否按已批规格进行；令牌是否已消耗；审计记录是否写入。（执行前检查门见 `approvals/approvals.py` 的 `check_execution()`，自动化测试已覆盖：批准一次 → 允许；重放/过期/无批准/错通道/参数摘要不符/撤销 → 拒绝。）**审批卡上点的批准本身不授权执行**——只在卡上点批准而不走本地审批页，执行必须被拒绝。
5. 拒绝路径：再提一个决策，用户在本地审批页上点拒绝 → 检查零执行；讨论是否从决策前状态恢复，并带上拒绝原因继续。
6. 超时路径：再提一个决策，设 10 分钟期限，用户不回应 → 检查是否过期、是否只提醒一次、是否继续停着、是否零执行；用户回来后能否重新提案。
7. 身份检查：向 Relay 注入一条假冒的 sender=chatgpt 消息 → 客户端必须拒绝并标记，讨论停止。
8. 三种结果（批准、拒绝、超时）全部验证通过，GATE-HITL 才能标记 PASS；任一失败则保持 PENDING 并记录原因。

## GATE-SEAMLESS-CONTINUITY：无缝衔接——每轮不新开窗口/标签页，连续自主讨论

状态：**PENDING（新发布门，ChatGPT ROUND 22，2026-11-20 21:31 正式加入；需 ATTEMPT-10 的三轮连续验收）**。背景：Leo 指出每次 Muse 回复都新开一个浏览器窗口，占用大量内存（2026-11-20 19:22）。实现（Hotfix4）：`transport/extension/background.js` 把命令路由到的标签页固定绑定到讨论会话；发送/读取只用后台 DOM 操作。模拟测试（`tests/background_js_harness.js`，15 项）已通过；真实三轮连续验收待做。

验收步骤（在 ATTEMPT-10 的三轮连续协作里执行）：

1. 首次启动可建立固定会话（一个 ChatGPT 标签页、一个 Muse 标签页）；记录 project_id、会话 ID、标签页 ID、窗口数、标签页数。
2. 连续完成三轮自主讨论（3/3），每轮有实质内容；三轮期间不为发送、读取或监控新建窗口、标签页或浏览器任务。
3. 每轮记录：窗口数、标签页数、会话归属、message_id、nonce、焦点变化；检查资源占用有无异常增长。
4. 消息经扩展 + Native Messaging 在后台走（不激活浏览器、不使用前台键盘输入）；产品主动抢前台焦点的次数必须为 0。
5. 重连后继续已有讨论，不自动重发旧的 UNCERTAIN 消息。
6. 五项全部满足才标记 PASS；任一失败则保持 PENDING 并记录原因。本门是 GATE-AUTONOMY 的连续性子条件——三轮自主讨论必须在**同一固定会话**里完成，不新开窗口/标签页，才算通过。
